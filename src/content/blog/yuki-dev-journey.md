[Yuki](https://github.com/YuanYeYouTao/Yuki) 的第一個 commit 是 2026 年 7 月 23 日，3.8.4 在 9 月 25 日發布。兩個月多一點，大約 700 個 commit、130 個合併的 PR，版本號從 0.1 一路跑到 3.8.4。

版本號跑得這麼快，一部分是因為我習慣小步發布，另一部分是因為中間推倒重來了好幾次。這篇不介紹功能（[上一篇](/blog/introducing-yuki/)做過了），而是照時間回頭看：每個階段在解決什麼問題、哪些東西後來被我刪掉、以及為什麼。

## 第一階段：先讓它記得人（0.1 → 1.0）

0.1.0 只是一個能在 QQ 上接模型回話的 bot。兩天後的 1.0.0 就是一次破壞性改版：刪掉之前所有的會話資料，重建成**以人物為中心**的 schema。

幾個從那時候定下、到現在都沒變的決定：

- **永久事件帳本**：每一則收發的訊息都寫進 `chat_events`，包括訊息段、回覆關係和群號。群裡沒有 @ Yuki 的訊息也會保存下來。
- **記憶是從帳本提煉出來的**：背景工作每 30 秒或累積 10 則訊息就批次整理一次人物記憶、群記憶和「某人在某群」的記憶。
- **全文檢索**：SQLite FTS5 搭配 trigram，三個字以上走全文檢索，短詞走有範圍限制的 `LIKE`。

回頭看，「帳本是唯一原文、其他都是衍生資料」是整個專案最重要的決定。後來記憶系統重寫了兩三次、對話摘要換了好幾種策略，都是因為原文一直都在，才敢砍掉重建。

## 第二階段：一天一個能力（1.1 → 1.9）

接下來五天幾乎每天發一到兩個版本：

- **1.1 聯網搜尋**：接 Tavily。比較有意思的是來源處理——模型預設不顯示網址；使用者問「來源呢」的時候，由**後端**把資料庫裡真實的搜尋來源渲染出來，模型不能自己拼連結。這是我第一次明確感覺到：能交給程式保證的事，就不要交給 prompt。
- **1.2 關係系統**：每個人有 0–100 的好感度和信任度，由獨立的評價器調整，單次最多變動 ±2，信心低於 0.75 的判斷直接作廢。而且**好感度跟權限完全脫鉤**，就算好感度 100 也拿不到管理工具。
- **1.3–1.4**：用自然語言管理設定、雙模型看圖（視覺模型先描述，主模型再回答）、圖片的提示注入隔離。
- **1.5 可信時間與自動化**：模型對「現在幾點」的判斷不可靠，所以時間由後端提供；定時任務也在這時候加進來。
- **1.6 Planner-first 改寫**與 Plugin API v1。
- **1.7–1.8**：持久化的表情包系統，以及完全本地的語音合成（Genie-TTS，中日雙語）。
- **1.9「Rising Sea」架構**：`ModelRouter` 按任務分派模型、`PromptCompiler` 讓每次請求都有穩定的靜態前綴（對 prompt cache 很重要）、`CapabilityDescriptor` 統一描述每個工具的效果、風險和權限。

這個階段的問題是加得太快，很多功能各自長出了一套判斷邏輯。

## 2.0：版本號跳大版，是因為刪東西

2.0.0 沒有新功能，而是一次「破壞性精簡」：刪掉已經脫離主流程的管理員意圖路由、1.5 時代的群聊自主候選器，以及它那一堆信心值、冷卻時間和每小時計數器。**Planner 成為一般聊天唯一的決策邊界。**

之後同樣的事又發生了好幾次：3.8.0 刪掉整條舊的身份模型；3.8.3 刪掉 3.3.1 才加進來的聯網路由器，也撤掉了麥當勞 MCP。我慢慢接受了這件事：一個功能加進來之後被證明是錯的方向，最好的處理方式就是乾脆刪掉，而不是留著相容層。

## Tool Kernel 與 MCP（2.1）

2.1 加入統一的 Tool Kernel 和 MCP client。當時接了麥當勞官方的 MCP，Yuki 真的可以查門市、看菜單、建立待付款訂單（只給付款連結，永遠不會自己付款）。

這件事讓我修掉了一個很實在的漏洞：原本 `mcp_gateway` 的唯讀外殼可以直接執行任意遠端工具，繞過策略檢查。修完之後，每一次 MCP 呼叫都要先解析成已啟用、已發現、通過篩選的工具，再用那個工具**真實的**效果與風險走同一個策略引擎。另外還加了「這次呼叫到底有沒有造成修改」的三態判斷，避免同一輪重複下單。

## 記憶重寫（3.0 → 3.5）

7 月 31 日到 8 月 1 日，3.0 從 alpha 到 rc 再到正式版，只花了兩天，內容是整個記憶系統重做成 Memory V2：

- 身份安全：記憶的讀寫範圍嚴格跟著「這是誰、在哪個場合說的」。
- 查詢驅動的詞法檢索，加上 Qwen embedding 的混合 RAG。
- 能感知衝突的生命週期：新事實和舊事實矛盾時，不是直接覆蓋。
- 可控的帳本重建：記憶壞了，可以從事件帳本重新提煉。

之後幾個版本讓 Yuki 有了**自己的記憶**（3.2）、長篇的自我反省（3.4.6），以及 3.5 的 Dream——在背景把零散的記憶合併整理，檢索時用 MMR 避免召回一堆重複的東西。

到 3.8.2 我做了一輪專門的「記憶與查證可靠性」收尾：Main Agent 有固定的查證流程，工具可見、實際查詢、實際使用分開記錄。發布說明裡我特別寫了一句：**不宣稱消除幻覺**。能做的是讓每一條記憶都追得回真實來源，而不是保證模型不會說錯。

## 長對話（3.6 → 3.7）

群聊是無限長的，context 不是。3.6.1 加了分層的對話摘要（Rollup）：

1. 切窗的當下先用**不呼叫模型**的抽取式摘要頂上，保證不卡住聊天。
2. 背景再用較便宜的模型把同一段升級成結構化摘要，並一層一層往上合併。
3. 原文永遠留在帳本裡，模型需要時可以用 `get_chat_history_around` 回頭讀。

同一時期 3.6.0 把主流程換成 Conversation Runtime，工具則改成按命名空間暴露，用 FTS5 索引讓模型「搜尋」自己需要的工具，而不是每次把所有工具的 schema 全塞進去。

## 一個資料庫，一個永久的 Yuki（3.8.0）

早期的 Yuki 是綁在某個 QQ 帳號上的。換帳號、換網關（NapCat 或 SnowLuma），記憶和關係就接不上。

3.8.0 的答案是 canonical 身份模型：**一個資料庫對應一個永久的 Yuki**。Person、Space、Presence 成為唯一的身份模型，私聊按人、群聊按空間聚合；關係、記憶、偏好和自動化都不再綁定 Yuki 用的是哪個 QQ。

遷移過程是整個專案最緊張的一段：先寫影子資料、雙寫、做稽核過的回填預檢、切換，最後才刪掉舊路徑，並把資料庫遷移重設成一個凍結的 baseline。舊版本沒有 downgrade，回退只能還原同一時間點的資料庫快照。

## 從聊天機器人到 Agent（3.8.2 → 3.8.4）

九月的主題是讓 Yuki 真的能**做事**：

- 直接看原生圖片、影片抽幀、讀 PDF / DOCX / XLSX 附件，語音則透過 Qwen 轉成文字。
- **持久工作環境**：跑在 gVisor 沙箱裡的 Linux 容器，能保存檔案、跑 Python / Node.js / Shell、裝套件、在背景執行任務；Bot 重啟時任務還能繼續。
- 持久化的 Work 與子 Agent：任務可以跨訊息、跨重啟地續跑，中途也能改方向。
- **統一回執**：任務被接受、執行完成、訊息送達分別記錄。README 裡有一句我很在意的話——**呼叫了工具，不等於結果已經交付。**

3.8.4 還有一個看起來很小、其實影響很大的改動：發言變成 Yuki 自己的顯式行動。Main Agent 要主動呼叫 `send_message` 才會說話，可以分幾則發送，也可以回 `NO_REPLY` 選擇沉默；排程器不再自動把模型最後的輸出轉發出去。

## 貫穿全程的問題：什麼時候該開口？

如果只能挑一條線來看 Yuki 的演化，我會選「群聊自主參與」。它幾乎每個大版本都被重做一次：

- **1.0**：收集 8 秒內的訊息，只有回覆、提到 Yuki、群裡提問或與記憶相關時才交給模型判斷要不要說話。
- **1.5**：獨立的自主候選器，加上信心值、冷卻、每小時次數上限。規則越疊越多，還是很容易在奇怪的時機插話。
- **2.0**：整個刪掉，交給 Planner。
- **3.7.1**：參與門檻預設調到 80。當時 changelog 裡寫的是：「`0` 幾乎總會插話。」
- **V6**：拆成獨立的 [Yuki Semantic Participation](https://github.com/YuanYeYouTao/Yuki-Semantic-Participation) 函式庫，9 月 22 日接進主線。

V6 的想法是：不再用「沉默滿幾小時就可以說話」這種硬規則，而是把參與狀態寫成一組連續的方程。由一個觀察模型（Jev）判斷訊息是不是在邀請 Yuki、是不是在延續剛才的話題；控制器維護群裡的交流熱度、Yuki 最近說了多少話、上次發言有沒有人回應，然後算出「現在開口」的淨價值，只有正值才提出機會。

其中我最喜歡的一個性質是：當一個群完全沒人說話時，

```text
ℓ → 0（交流背景衰減），g → 1（Yuki 自身恢復）
lim U_self = -0.05 < 0
```

也就是說，一個長期沉寂的群會**自然**回到安靜，不需要任何「禁言幾小時」的特例；而最近有足夠交流的群，就算隔了幾個小時，也仍然可能出現一次自然的開口機會。另外，發言沒人理會之後，後續主動開口的頻率會降低。

控制器提出的只是「機會」。能不能執行，還要 Host 核對來源、群授權、權限和工作佔用，最後 Main Agent 依然可以選擇不說話。語義參與目前**預設關閉**；回放實驗用的是合成的群聊軌跡，只能驗證機制，真實群聊的長期效果還需要觀察。

## 回頭看，學到的幾件事

1. **帳本優先。** 原文只存一份，記憶、摘要、關係都是可以重算的衍生資料。這讓每一次重寫都有退路。
2. **敢刪。** 2.0、3.8.0、3.8.3 都是刪除大於新增的版本。相容層會讓錯誤的設計多活很久。
3. **權限在後端，不在 prompt。** 好感度不影響權限、來源由後端渲染、Yuki 自己發起的任務不能借用管理員的權限——這些都不是靠「請模型不要這樣做」來保證的。
4. **呼叫了 ≠ 做完了。** 接受、執行、送達分開記錄，恢復的時候才知道哪些可以重試、哪些絕對不能重發。
5. **老實寫限制。** 發布說明裡寫清楚「沒有做到什麼」，比列一堆指標更有用，對未來的自己也是。

開發方式上，比較大的改動我都會先寫成任務書，定清楚合同和驗收條件再動工；現在 `docs/architecture` 裡已經累積了二十幾份。事後看，這些文件比程式碼本身更能說明當時為什麼那樣做。
