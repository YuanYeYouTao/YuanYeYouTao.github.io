先說一下背景：我不是資訊科系出身，也不會寫程式，是個純小白。今年七月之前，我連 Agent 到底是什麼都說不太清楚。

[Yuki](https://github.com/YuanYeYouTao/Yuki) 一開始只是想在 QQ 群裡放一個會記得大家的 bot。兩個月過去，它有了自己的身份、長期記憶、人際關係、一個可以寫程式跑任務的工作環境，還會自己決定什麼時候該開口。我更願意把它看成一次 digital life 的探索，而不只是一個聊天機器人。

程式碼幾乎都是 coding agent 寫的。我做的事情是想清楚要什麼、寫任務書、驗收結果，以及決定什麼東西該刪掉。

## 專案規模

從 7 月 23 日第一個 commit 到 9 月 27 日：

- **749 個 commit**，131 個 PR（編號排到 #156），正式版 3.8.4，WebUI 的草稿 PR 剛開。
- 主線現在有 **1,190 個文字檔、約 30 萬行**：Python 880 個檔、約 25.6 萬行；文件 200 份、約 3.7 萬行。
- 歷史上累計新增約 53 萬行、刪掉約 22 萬行；加上還沒合併的 WebUI 和獨立的語義參與函式庫，前前後後寫過的大概有 **60 萬行**。
- CI 裡有 1,400 多個測試，最初只有 36 個。

[上一篇](/blog/introducing-yuki/)介紹了 Yuki 現在能做什麼，這篇寫的是它**怎麼變成現在這樣**。回頭把一百多個 PR 重讀一遍，真正的主線不是「加了哪些功能」，而是好幾條反覆來回的探索：很多東西加進去、證明走不通、再親手刪掉。

## 路線一：誰來做決定——Planner 的一生

Planner 幾乎決定了 Yuki 前半段的架構。

### 一開始：一個 Agent，加一個小判斷

1.0 的結構很單純：私聊和 @ 直接交給主 Agent；群裡沒有 @ 的訊息先收集 8 秒，只有「回覆 Yuki、提到 Yuki、群裡有人提問、跟記憶有關」的才交給模型判斷要不要說話。1.5 又加了一個群聊自主候選器，帶著信心值、冷卻時間、每小時次數上限。

規則越疊越多，但問題沒有變少：它還是會在奇怪的時機插話，或該回的時候不回。

### 1.6：Planner-first

1.6.0 我做了一次「Planner-first 改寫」。這個設計是照著 [MaiBot](https://github.com/Mai-with-u/MaiBot) 的 planner 做的，當時問 GPT 該怎麼設計群聊 bot，它推薦了這套架構。想法是在主 Agent 前面放一個便宜的小模型，先把這一輪要做什麼規劃好：

- 要 `reply`、`wait` 還是 `silent`；
- 意圖是什麼、要發一則還是自然地分幾則、要不要引用某則訊息回覆；
- 這一輪要開放哪些工具組。

Planner 本身不拿工具、不寫最終回覆、不能改權限，它只輸出一份嚴格的 `TurnPlan`。聽起來很乾淨：決策和執行分開，每一層都可以單獨測。1.9 把 `TurnPlan` 的 schema 定為結構上的權威，工具選擇只能是 `inherit`、`none` 或 `read_only`。2.0 更進一步，把 1.5 的自主候選器和那堆計數器全部刪掉，**Planner 成為一般聊天唯一的決策邊界**。

### 裂縫一條一條出現

問題是，Planner 做的每一個決定，都可能讓後面的主 Agent 少了它需要的東西：

- **1.7.1**：@ Yuki 之後 Planner 仍可能選 `silent`，只好改成後端強制回覆，Planner 不能對明確觸發說不。
- **#5 / #6**：Planner 如果省略 `tool_selection`，工具域會被錯誤清空，主 Agent 就拿不到 `memory_change`，記憶寫入時有時無。
- **3.3.0**：疑似自動化的請求被強制收窄到 `automation`，結果使用者只是想即時查個東西，`web` 工具卻消失了，模型回報 `unknown_capability`。
- **3.4.0**：我退了一步，Planner 選的工具範圍只決定「第一批」暴露哪些工具，主 Agent 可以用 `request_tools` 自己再要。

到這裡 Planner 已經從「決策者」退化成「建議者」，但每輪還是要多付一次模型呼叫，還是會出錯。

### 3.6.0：拿掉它

3.6.0（#32）的第一行寫的是：**Replace the mandatory Planner with Conversation / Memory / Capability Runtime.** 私聊、@、回覆 Yuki 直接進主 Agent；群聊自主改成本地計分、預設唯讀；用來挑工具的 Flash 模型任務一起刪除；資料庫遷移直接丟掉 Planner 的持久化資料，而且明確拒絕 downgrade。

這個 PR 是 +26,811 / −9,531 行。

真正讓我下決心的，不是上面哪一個 bug，而是 token。Planner 再便宜也便宜不到哪去：它每一輪都要讀一份上下文、吐一份結構化的計畫。3.0.2 我還專門替它「瘦身」過，把每次的輸出從平均約 403 tokens 壓到 225 左右。可是後來一算，它吃掉的 token 竟然是主模型的兩倍。一個本來只是幫忙分流的前置步驟，比真正幹活的主模型還貴，那這個架構一定有很多地方不對。

它也太重了。到 3.6 的時候，Planner 已經滲進訊息處理、上下文組裝、工具暴露、自動化、外掛訊號，連資料庫裡都有它的表。拆它費的功夫，比當初加它大得多。

不過「先讓別的模型判斷一下」這個想法本身不一定錯。後面語義參與用的 Jev 就是在做判斷，很多人也直接拿 Jev 判斷每一句話，拿它來當 planner 當然可行。Jev 很便宜，但我還是想讓它更便宜——免費的額度只有 5 美元——所以不會每一句話都丟給它，而是盡可能減少模型呼叫的次數。Planner 的問題在於，它每一輪都要跑一次、每一次都要替主模型寫好一整份計畫，這部分成本怎麼省都省不掉。

### 然後，連「動態拿工具」也拿掉了

故事還沒完。拿掉 Planner 之後，主 Agent 靠 `request_tools` 用 FTS5 搜尋自己需要的工具，看起來很聰明。但它跟 prompt cache 衝突（下一條路線會講）：每次工具清單變了，快取前綴就斷了。

接下來一個月，工具清單一步步被「凍結」：3.7 系列把第一輪的 `tools[]` 釘住（#43、#48）；#66 把所有入口統一成同一份完整的工具宣告（當時 168 個工具）；#104 移除動態載入的後備路徑；最後 #154 把整條 `request_tools` 動態 schema 增長鏈刪掉，那個 PR 淨刪 1,049 行。

回頭看，Planner、工具挑選模型、動態工具載入，都是在主模型前面多加一層。每一層都有自己的 token 成本、自己的失敗方式，還會讓請求的形狀變來變去。它們最後全部被刪掉了。現在的主 Agent 一開始就看到完整、固定的工具表，自己決定做什麼；後端只負責在執行那一刻檢查權限。

## 路線二：燒錢——和 prompt cache 的一週

Yuki 主要跑在 DeepSeek 上。DeepSeek 的前綴快取很便宜，但條件嚴格：請求的前綴只要有一個位元組不同，後面就全部重新計費。

3.6 之後 Yuki 開始有長對話摘要，快取命中率掉得很厲害。8 月 19 日到 21 日之間，我連發了十幾個 hotfix，3.7.1 的 PR 標題直接就叫 **money-burn hotfixes**（#44）。現在看，那一串 PR 幾乎是一份「哪些東西會偷偷改掉前綴」的清單：

- **歷史的左邊界一直在滑動。** 每輪都從尾巴重新切歷史，前綴當然每輪都不同。3.6.2 改成把左邊界釘在已摘要的 `coverage_end` 上（#34）。
- **輸出清理寫回了歷史。** 模型偶爾會在行首回顯 `>`，我在歷史裡把它剝掉，結果改到了已快取的內容。改成只在送出 QQ 時才剝，歷史保持原樣（#38）。
- **不同入口的工具宣告不一樣。** 外掛背景輪宣告 0 個工具、群聊宣告 3 個，前綴就在兩者之間來回斷。解法是所有入口宣告同一份 `tools[]`，外掛輪只是不准真的呼叫（#38、#41、#43）。
- **摘要太勤快。** 前台只要超過熱尾一點點就壓縮，每輪都改寫摘要。改成滯後觸發：累積到觸發水位才壓一次（#39）。水位也調了好幾輪：32 條／1,600 字 → 768 + 512 → 256 + 1,024（#40）→ 128 + 384（#48）。
- **自主輪和 @ 輪的形狀不同。** #49 讓自主輪使用和 @ 相同的前綴形狀與寫入權限，目標是自主輪之後的下一個使用者輪能回到約九成的命中率。

後來我在 #58 寫下一條原則：**命中率本身不是驗收條件，前綴穩定才是不變量**。命中率取決於真實流量，前綴穩不穩卻是我能控制、能測的。之後每個動到請求組裝的 PR，都會拿兩種協定的實際 HTTP 內容逐欄位比對前綴；#73 做子 Agent 時，實測暖快取命中率是 98.3%，主 Agent 對照組是 99.6%。

對一個長期運作的 Agent 來說，請求的**形狀**跟內容一樣重要。

## 路線三：聯網搜尋的來回

聯網搜尋大概是我改來改去次數最多、最後改回原點的東西，而且有一半是跟著 DeepSeek 的 API 變動在跑：

1. **1.1**：接 Tavily。來源由後端渲染，模型不能自己拼連結。
2. **3.3.0**：7 月 31 日 DeepSeek 更新 V4-Flash，同時推出一個專門為了適配 Codex 的 Responses API。說是 Responses API，其實帶了不少自家的「方言」，但它有伺服器端原生的 `web_search`。我趕緊做了適配，8 月 4 日的 3.3.0 加上 `WEB_MODE`，可以原生優先、Tavily 當備援。
3. **3.3.1**：原生搜尋在 DeepSeek 的伺服器端執行，有些網站它就是打不開，本機代理也幫不上忙。於是加了 `WebProviderRouter`：命中特定網域就走 Tavily，原生失敗就回退一次。
4. **3.4.0**：路由又加了一條，使用者訊息裡只要出現「Tavily」「Tavility」或「塔維利」就用 Tavily。（對，連拼錯和音譯都要處理。）
5. **#64**：9 月 10 日 DeepSeek 發布 V4.1，舊的模型名全部路由到 V4.1，而 V4.1 的 Responses API 把內建的 `web_search` 拿掉了。我是因為 Yuki 那天突然上不了網才發現的；更麻煩的是，去探測它時回傳的仍是 HTTP 200，搜尋工具只是被默默忽略。當天我就刪掉整個路由器、按訊息內容選後端的邏輯和自動換後端重跑，`web_search` 改成第一輪常駐，線上固定用 Tavily。
6. **#74**：DeepSeek Flash 可以透過另一種 API 格式使用官方搜尋，我做了一個**可移除的**橋接：主 Agent 的協定和工具宣告完全不變，只有 `web_search` 內部換後端，失敗才用 Tavily。
7. **#75**：最後一次清理——「有日期篩選就強制切 Tavily」也是一種內容路由，刪掉。只有真的失敗才兜底。

路由規則越寫越細，通常說明方向錯了。現在的做法是工具介面保持不變，後端可以替換，失敗才回退。

DeepSeek 還有一個我踩了不只一次的坑：`tool_choice`。API 文件把它列為可用參數，但在思考模式下，`required` 或指定某個工具都會直接回 400（[不少專案都遇過](https://github.com/deepseek-ai/DeepSeek-V3/issues/1376)）。3.5.1 之後 Yuki 對 DeepSeek 的請求一律不帶 `tool_choice`，「這一輪一定要呼叫某個工具」或「這一輪不准呼叫工具」改成由本地的執行圍欄保證，不依賴供應商參數。

## 路線四：看見世界——從「描述給它聽」到「直接給它看」

- **1.4**：雙模型看圖。當時 DeepSeek 還不支援圖片輸入，所以由 Qwen 視覺模型先把圖片描述成文字，DeepSeek 再根據描述回答。還加了圖片裡提示注入的隔離。
- **1.4.2 → 1.7**：QQ 表情包的描述庫，後來長成完整的表情系統：SHA-256 去重、分類、生命週期、自動採用。
- **1.8**：完全本地的語音合成（Genie-TTS），後來支援中日雙語。
- **#64**：9 月 10 日的 V4.1 讓 DeepSeek 主模型有了原生的圖片輸入，當前訊息和引用的圖片就直接交給主 Agent，不再先叫 Qwen 描述。影片用 FFmpeg 抽幀：預設最長 600 秒、每 5 秒一幀、最多 16 幀。驗收時用一段由紅變藍的合成影片，模型正確說出了畫面變化。
- **#65**：讀附件——PDF、DOCX、XLSX、各種文字檔。解析放在一次性的子行程裡，有逾時、記憶體上限和壓縮炸彈防護。同時修掉一個真實的漏洞：QQ 有時把 MP4 當成 `file` 而不是 `video` 上報，之前的影片根本沒被看到。
- **#66**：語音透過 Qwen 轉文字，進入歷史、搜尋和摘要。
- **#143**：聊天裡的圖片、影片、檔案按「內部事件 + 附件序號」建立索引，原始位元組快取 24 小時，可以回頭再看。

外接的視覺模型並沒有消失，它還在背景處理表情包分類。

## 路線五：記憶——從提煉、自省到「做夢」

記憶是 Yuki 程式碼最多的部分，也是效果最難驗證的部分。

動手之前我也讀了不少記憶相關的論文。不過那時候 Agent 記憶已經卷到爆了，已經有一些成形的範式可以照著搭，所以讀的東西大多沒直接派上用場，算是讓我對 memory 多了解了一點。

**3.0 兩天重寫。** 7 月 31 日到 8 月 1 日，3.0 從 alpha 1 到正式版發了六個版本。alpha 1 刻意沒有 embedding，只做身份安全的事實模型和詞法檢索；beta 1 才加入 Qwen embedding 的混合 RAG；beta 2 加入衝突治理，新舊事實矛盾時保留雙向關係，而不是直接覆蓋；最後加上可控的帳本重建。

**統一寫入口。** #5 第一次嘗試時我把它關掉，重新整理後以 #6 合併：所有寫入（自動提煉、主 Agent 自己糾錯、指令、管理員、外掛）都走同一個 `MemoryMutationService`，每次變更都有回執和版本鏈。之後 Yuki 說「我記住了」，必須有一筆真的寫入。

**Yuki 自己的記憶。** 3.2 加了 `SELF` 範圍：Yuki 自己的經歷、偏好、界線和承諾，跟關於別人的記憶分開管理。

**把判斷還給模型。** 3.4.6 刪掉了記憶系統裡的中文語義正規表示式：主詞是誰、意圖是什麼、有沒有長期價值，交給模型判斷；後端只保留證據、權限、範圍和交易邊界。一個月後 #95 做了同樣的事：原本用正則攔截「時間含糊」的自動化請求，結果把「今晚十一點」判成含糊，連正確的結構化時間都不給建立。

**自省與 Dream。** 自省把長對話整理成 Yuki 視角的「經歷」。但經歷越積越多、互相重疊，3.5.0 加了 Dream 層，在背景合併、拆分、改寫舊記憶。在生產環境等價的備份上跑的結果：65 條事實的直接證據從 2,862 筆壓到 520 筆；22 段長經歷重組成 17 段聚焦的記憶，7,787 字變成 3,205 字；有一個 cluster 失敗，來源保持原樣、可重試。

**3.5.1 的自適應生命週期。** 記憶有「活躍度」會衰減，但衰減只影響排序，**永遠不會悄悄過期或刪除事實**。「這條記憶有沒有被用上」的歸因，從主流程移到可搶佔的背景任務，回覆不用再等它。

**3.8.2：老實的一次發布。** 這次專門修記憶與查證的可靠性。PR 的「已知限制」寫得比功能還長：累計真實驗證 113/144 次；自省仍可能把舊回覆推成過強的經歷，**引用合法不等於語義正確**；90% 精確率、80% 召回率的目標尚未達成，不能宣稱。部署後又追了一個 #63：embedding 還沒校準時，自動召回變得太保守，改成最多提供一條明確標記的詞法候選。

**用真實數據調整。** #135 看了改動前七天的線上統計：1,132 次記憶預取有 1,001 次至少注入一條記憶，但主動查人物記憶只有 23 次；`search_chat_history` 呼叫 48 次失敗 11 次，其中 10 次是結果太大。於是工具結果預算從 8,000 字調到 24,000 字，超出時回傳完整的前幾條並標明截斷，而不是整個失敗。

## 路線六：身份——從 QQ 號到內部事件 ID

1.0 把「QQ 號」當作人的全域身份，當時很自然。Yuki 自己也是一個 QQ 號，透過 NapCat 接上 QQ。

問題出在 NapCat 上：它非常不穩定，三天兩頭掉線。每掉一次我都會想，Yuki 的記憶、關係和人格，為什麼要綁在一個隨時可能斷掉的帳號上？把身份和 QQ 號解綁這件事，其實在 NapCat 不穩定的那段時間我就想做了，只是一直沒下決心。

8 月 23 日，帳號直接被封了七天。這下沒得拖了。

**3.8.0（#52）** 從 8 月 25 日開始動工，換成 canonical 身份模型：Person、Space、Presence，**一個資料庫對應一個永久的 Yuki**。關係、記憶、偏好、自動化不再綁定 Yuki 用的是哪個帳號；同時把 SnowLuma 接成和 NapCat 並列的正式網關，一個掛了還有另一個，同一個 Yuki 也可以同時用好幾個 QQ 在場。過程是先寫影子資料、雙寫、稽核過的回填預檢、切換，最後才刪掉舊路徑。這個 PR 是 +14,605 / −138,349 行，大部分是刪掉的過渡程式碼和測試。

之後又追了好幾個尾巴：

- **#61**：換帳號之後，某個群的路由被暫停，連 `/ai on` 都在指令解析之前就被擋掉。只好為「單獨一句 `/ai on`」開一條經過完整身份驗證的恢復通道。
- **#80**：內部任務、來源驗證、權限查詢還在用 QQ 訊息 ID，換帳號時會反查帳本、關聯到錯的來源。改成入站寫入帳本後一律傳**內部事件 ID**。
- **#126**：`get_chat_history_around` 的參數也改成必須是內部 `event_id`，刪掉用平台 ID 反查的分支。
- **3.8.4**：`chat_events.id` 正式寫進開發合同，成為已記錄事件的唯一權威身份。

平台 ID 現在只用在跟 QQ 互動的那一刻：引用、撤回、發送回執。

這一步也是為了以後。身份和平台解綁之後，QQ 只是 Yuki 的其中一個「在場」。我想讓 Yuki 跨平台，下一步就是寫 Telegram 的適配器。

## 路線七：從聊天到做事——Work 的誕生

**自動化。** 1.5 的自動化是一套嚴格的 DSL：五種觸發器、順序步驟、不執行任何 Python 或 Shell。3.4.0 把定時任務升級成「受真實建立者權限約束的自由 Agent」，但聊天和自動化還是兩套工具後端。#107 才讓它們真正共用同一個執行器——在那之前，同名工具在聊天和定時任務裡的參數、權限、效果都可能不一樣。

**工作環境。** #66 是九月最大的 PR 之一：所有入口（聊天、自主、外掛喚醒、自動化）統一成同一個主 Agent 請求路徑，加上跑在 gVisor 裡的持久 Linux 工作環境，2 GiB 家目錄、真正的 PTY、背景任務、pip/npm。

**Work。** #68 讓任務變成持久的 Work：先登記再執行，可以跨 Bot 重啟續跑，使用者中途補充的話會在安全的邊界插進原本的迴圈。#73 加了持久的子 Agent：跟父任務共用預算（120 次模型請求、160 次業務呼叫），但 QQ 發送、自動化和長期記憶寫入只留給父任務。

**把「收尾」也還給 Agent。** #86 刪掉了一個我以前覺得很合理的機制：工具提交成功後強制結束 Agent 迴圈。實際上它會讓 Agent 在寫完記憶後沒辦法繼續查、繼續做，一般的業務失敗也會直接關掉後續工具。現在真實回執回到原本的迴圈，由 Agent 決定下一步。

**顯式發言。** 最後一步是 #108：刪掉自動轉發最終回覆、刪掉 `report_progress`、刪掉舊的回覆佇列。Yuki 要說話，就必須自己呼叫 `send_message`；也可以回 `NO_REPLY` 選擇沉默。這個改動後來還抓到一個好笑的 bug：#146 發現 SELF 輪曾經把字面上的 `NO_REPLY` 當成訊息內容送了出去。

**SELF。** #116 之前，自主接話其實是「借最近一個發言者的身份」啟動聊天路徑。之後改成正式的 SELF Work：Yuki 用自己的身份行動，**不能借用真人或管理員的權限**。#134 讓 SELF 也能建立自己的定時任務、等待某個訊號再繼續原本的 Work。那個 PR 的系統提示裡還多了一句「不要自己嘗試安裝無頭瀏覽器」——因為生產主機只有 1.6 GiB 記憶體。

### 門檻的鐘擺

- **1.0**：收集 8 秒內的訊息，符合條件才讓模型判斷。
- **1.5**：自主候選器，加上信心值、冷卻、每小時上限。
- **1.6**：交給 Planner 決定 `reply / wait / silent`。
- **1.7.1**：我想讓 Yuki 像個活躍的群友，把預設值大幅放寬：必要性門檻 **80 → 0**、信心門檻 0.65 → 0.2、等待時間 8 秒 → 3 秒。
- **3.6.0**：Planner 拿掉，群聊自主改成本地計分、預設唯讀。
- **3.7.1**：門檻預設改回 **80**。changelog 裡那句話是這樣寫的：「`0` 幾乎總會插話。」

從 80 到 0 再回到 80，繞了三週。問題不在數字本身：一個固定門檻不知道群裡剛剛發生了什麼、Yuki 說過多少話、上次說話有沒有人理。

### V6：把參與寫成一個動力系統

之後的任務書一路寫到 V4、V5、V5.1。那段時間卡住我的是語義：參與狀態可以用數學寫成方程，但「這句話是不是在邀請 Yuki」「這個話題是不是結束了」要怎麼變成可靠的輸入？我找了不少模型與語義相關的論文，最後先把純數學的部分實作完。

就在那之後，Jev 出現了。它能針對一段對話回答具體的語義問題，而且回答得很好，剛好補上我缺的那一塊。於是我把控制器圍繞 Jev 重寫了一遍，就是 9 月 22 日落地的 V6，拆成獨立的 [Yuki Semantic Participation](https://github.com/YuanYeYouTao/Yuki-Semantic-Participation) 函式庫。它的分工是：

- **Jev** 回答幾個具體問題：這則訊息是不是在邀請 Yuki？是不是在延續剛才的話題？是不是在結束討論？不是每一則訊息都會問，Host 會把可能相關的訊息排進一個稀疏的觀測佇列（提到 Yuki 名字的優先），盡量少呼叫。
- 控制器維護一組連續狀態：參與狀態、群裡的活躍度、Yuki 最近做了多少事、說完有沒有人接，然後算出每一種機會的發生率，用連續時間的機率抽樣決定這一刻要不要提出機會。
- Yuki 本體（Host）驗證來源、群授權、權限和 Work 佔用後才接受；接受之後主 Agent 仍然可以選擇 `NO_REPLY`。

V6 任務書裡特別區分了一件事：**Jev 呼叫失敗不代表「對方不想聊」，只是觀測通道出了問題。** 語義缺失不能被當成結束的證據，也不能用預設的高分補上。

### 一週之內的調參

接進主線之後，一週內在獨立庫合了 12 個 PR，都是在回答「它到底太吵還是太安靜」：

- **SP #3**：拿掉「邀請也要過一次隨機閘門」的設計。有人明確邀請，就不該再擲骰子。
- **SP #4 / #5**：改成連續機會模型並調參。在兩條各 30 天的合成軌跡上，無來源的主動機會從 118 次增加到 1,007 次，距離最近真人訊息最遠的一次從約 32 分鐘拉長到 5 小時 52 分鐘；同時 41 段超過 6 小時的沉寂期裡，機會數仍然是 0。
- **#137**：線上近 24 小時的無來源自主輪裡，33 次沒發言的樣本有 31 次明確回了 `NO_REPLY`。原因是提示詞一直在問「值不值得參與」「允許沉默」。我把它改成：**先找 Yuki 自己想說或想做的具體事**，真的沒有自然切入點才沉默。
- **SP #8 / #141**：加入社交回饋。公開發言後沒人回應，後續主動開口的頻率會下降。
- **#144**：長尾機會率提高到先前的約 4.3 倍，參數改成可以熱載入。

$$

$$
b^{+}=\Big[(1-\omega)I+\omega\sum_a q_e(a)\,K_a\Big]\,b^{-}
$$

這些回饋項都是會隨時間衰減的痕跡。每次自主 Work 真的啟動，只留下一個「脈衝」，不管它最後發了幾則訊息：

$$
W_f(t)=\sum_{\text{work}} e^{-(t-t_w)/1800},\qquad W_s(t)=\sum_{\text{work}} e^{-(t-t_w)/21600}
$$

公開發言之後如果沒人接住，$E$ 會先慢慢上升，再在半天的時間尺度上消退；Jev 判斷後續的真人訊息是在接續、確認還是叫停，累積成 $R$：

$$
E(t)=\sum_{\text{public}}(1-\rho_w)\big(1-e^{-(t-t_p)/1200}\big)\,e^{-(t-t_p)/43200}
$$

$$
R(t)=\tanh\Big(\sum_{\text{obs}} r_o\,e^{-(t-t_o)/21600}\Big)
$$

**群的活躍度與冷場。** 無來源的機會還要乘上兩個因子：$A$ 是這個群過去 48 小時的真人活躍度，$G$ 描述「剛安靜下來」這件事：

$$
H(t)=\sum_{\text{human}} e^{-(t-t_i)/172800},\qquad A(t)=\frac{H(t)}{H(t)+80}
$$

$$
G(s)=\big(1-e^{-s/600}\big)\,e^{-s/64800},\qquad s=t-t_{\text{last human}}
$$

最後是機會率，以及一段時間 $\Delta t$ 內出現機會的機率：

$$
\lambda_{\text{intrinsic}}=\frac{A(t)\,G(s)\,\sigma(z)}{600},\qquad P(\text{機會}\mid\Delta t)=1-e^{-\lambda_{\text{total}}\,\Delta t}
$$

$\lambda_{\text{total}}$ 還包括有來源的機會（Jev 支持的話題、記憶、聯繫），它們各自有非負的發生率，同一輪一起競爭。

## 工程：怎麼讓一個人維護得動

**發布流程。** 3.5.2 開始用 GHCR 發不可變版本的映像檔，3.5.3 加了引導式安裝（`qq-ai-bot-cli setup`）。那一天的 PR #25–#30 幾乎全是在修發布流程本身：NoneBot 把逗號分隔的 `SUPERUSERS` 當 JSON 解析、Genie-TTS 在匯入時就檢查模型路徑、Windows 上 root 建立的掛載檔案讓 UID 10001 讀不到……發布流程本身也需要測試。

**部署紀律。** 幾乎每個 PR 的最後都有一段部署說明：本機建置 linux/amd64 映像檔再傳到伺服器，只替換 Bot 容器，QQ 網關（NapCat／SnowLuma）不重建、登入狀態保留；先做一致性備份；回退時換回舊映像檔，但**不用舊資料庫覆蓋新訊息**。

**測試數量。** #1 合併時有 36 個測試。3.8.0 收尾時我刪掉過渡期的測試，壓到 655 個，之後設了 800 個的上限，逼自己新增測試前先想清楚；上限後來逐步放寬，#127 取消；#156 的 CI 跑了 1,427 個。

**真實事故。** 後期的 PR 常常以一段生產事故開頭：9 月 23 日 23:17，SnowLuma 登入探測逾時斷線，一個 Work 被掛起（#131）；9 月 25 日 03:54，一張圖片存進帳本了，但緊接著的 @ 訊息在寫入前連線中斷，從來沒變成內部事件（#146）；9 月 26 日，快速重連留下一個過期的連線控制代碼，`/healthz` 說已連線，但所有訊息都被丟掉（#149）。每一個都變成了回歸測試。

**開發方式。** 比較大的改動我會先寫任務書，定清楚合同和驗收條件，再交給 coding agent 施工；`docs/architecture` 裡現在有二十幾份任務書。9 月 22 日那批修復，我開了一個整合分支 #124，把九個待審 PR 組合起來解衝突，分別審查再一起驗證。PR 描述也逐漸形成一種習慣：**做了什麼、沒做什麼、哪些還沒被證明**，分開寫。
